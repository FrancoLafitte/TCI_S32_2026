## 2. Comunicación y Frecuencia
* **Canal oficial de comunicación:** Grupo de WhatsApp del equipo.
* **Frecuencia mínima de encuentro:** Reuniones y sincronizaciones virtuales de forma variable, adaptadas a los distintos horarios de disponibilidad de los integrantes, priorizando los días jueves y fines de semana.

## 3. Convención de Commits
Usaremos el estándar de **Conventional Commits** para los mensajes de los commits:
* `feat:` para nuevas funcionalidades.
* `fix:` para corrección de errores (bugs).
* `docs:` para cambios en la documentación (como el README o este charter).
* `chore:` para tareas de mantenimiento, configuración o dependencias.

## 4. Reglas de Pull Requests (PRs)
* **Destino:** Todo PR va dirigido obligatoriamente a la rama `main` del fork del equipo, **nunca** al repositorio de la cátedra.
* **Aprobaciones:** Todo PR requiere como mínimo **1 review de aprobación de un compañero**. 
* **Regla de oro:** El autor del código **NUNCA** se mergea su propio PR (se cumple estrictamente el code review cruzado).
* **Nomenclatura de títulos:** Claros y descriptivos (Ej: `feat: agregar formulario de login` o `docs: actualizar charter`).

## 5. Definición de "Terminado" (Definition of Done - DoD)
Un cambio o feature se considera terminado cuando:
* El código compila y funciona correctamente sin romper lo que ya estaba hecho.
* Se respetó la convención de commits.
* Pasó por la revisión de un compañero y fue aprobado.
* Fue mergeado correctamente a la rama `main`.

## 6. Acuerdo ante Inactividad o Falta de Aporte
* Si un integrante no puede participar o no responde durante un plazo prudencial sin previo aviso, se intentará contactar por el canal oficial. Si la falta de comunicación o aporte persiste de manera injustificada afectando el desarrollo del trabajo, se le notificará al docente de la cátedra para buscar una solución equitativa para el resto del grupo.
